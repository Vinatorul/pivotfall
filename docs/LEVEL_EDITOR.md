# Встроенный редактор уровней

Статус: data-driven фундамент, редактор, все типы врагов и механизмов,
кампания Arena 01–08 и главное меню реализованы.

Дата: 30 июля 2026 года.

Цель — добавить к игре ограниченный редактор, в котором можно собрать
одноэкранную арену из уже существующих правил, сразу проверить её в игре и
сохранить как переносимый файл. Формат данных, общий runtime и первый
внутриигровой интерфейс уже образуют полный вертикальный срез.

## Выбранный формат редактора

Редактор будет отдельным внутриигровым режимом, а не плагином для редактора
Godot. Это позволяет:

- использовать один и тот же интерфейс в ПК- и Web-сборке;
- дать автору уровня цикл «изменил → `F5` → сыграл → вернулся» без работы со
  сценами Godot;
- отделить данные уровня от внутреннего устройства узлов;
- в перспективе импортировать и экспортировать пользовательские уровни без
  запуска чужого кода.

Поведение игрока, противников и механизмов по-прежнему реализуется обычными
сценами и скриптами проекта. Редактор выбирает только известные игре типы и
настраивает разрешённые параметры. Он не является универсальным редактором
Godot.

## Основной поток данных

```text
JSON-файл
    ↓
LevelDataCodec
    ↓
LevelDataValidator ──→ список ошибок и предупреждений
    ↓
LevelBuilder ──→ LevelRuntimeArena ──→ игровой тест
    ↑
LevelDraft ←──────── внутриигровой редактор
```

- `LevelDraft` — изменяемая модель открытого уровня и источник Undo/Redo.
- `LevelDataCodec` читает и записывает JSON, но не создаёт игровые узлы.
- `LevelDataValidator` проверяет структуру, значения и связи до сборки.
- `LevelBuilder` создаёт арену только из проверенных данных.
- `LevelRuntimeArena` содержит неизменяемый каркас экрана: фон, внешние стены,
  потолок, общую `DeathZone`, игровой UI, победу, падение и restart.
- реестр типов сопоставляет короткие идентификаторы вроде `patrol_enemy` с
  заранее включёнными в проект `PackedScene`. В JSON нет путей к сценам,
  скриптам и ресурсам.

Сборка проходит в два этапа. Сначала builder создаёт геометрию, механизмы и
существ и регистрирует их стабильные ID. Затем разрешает связи, например
`hinge.target_id`. Подсчёт противников и запуск арены происходят только после
полной сборки, а не в `_ready()` до появления динамических узлов.

Если validator находит ошибку, builder не оставляет частично собранную арену.
Предупреждения показываются автору, но не блокируют тест.

## Формат уровня

Уровень хранится в строгом версионированном JSON. Для первой версии:

- `schema_version` всегда равен `1`;
- координаты и размеры — целые пиксели в системе экрана 960×540;
- прямоугольник записывается как `[x, y, width, height]`, где `x` и `y` —
  левый верхний угол;
- позиция объекта записывается как `[x, y]` и соответствует origin его
  игровой сцены;
- будущая сетка редактора использует шаг 20 px, но это только привязка
  интерфейса: формат не округляет существующие арены;
- все объекты имеют уникальный ID, который не зависит от имени узла;
- неизвестные поля, типы и свойства считаются ошибкой, чтобы опечатка не
  превращалась в молча проигнорированную настройку.

Минимальное представление аналога Arena 01:

```json
{
  "schema_version": 1,
  "level_id": "arena_01_data",
  "title": "GRAYBOX / DATA ARENA 01",
  "objective": "СТОЛКНИ ВРАГА В ЯМУ ↓",
  "clear_message": "DATA ARENA ПРОЙДЕНА / ПЕРЕЗАПУСК...",
  "canvas": {
    "width": 960,
    "height": 540,
    "grid_size": 20
  },
  "objects": [
    {
      "id": "floor_left",
      "type": "solid_rect",
      "rect": [32, 496, 368, 44]
    },
    {
      "id": "floor_right",
      "type": "solid_rect",
      "rect": [560, 496, 368, 44]
    },
    {
      "id": "player_start",
      "type": "player_spawn",
      "position": [150, 450]
    },
    {
      "id": "patrol_1",
      "type": "patrol_enemy",
      "position": [360, 450],
      "speed": 65,
      "direction": 1
    }
  ]
}
```

Внешние стены, потолок и зона падения не повторяются в каждом файле: их создаёт
`LevelRuntimeArena`. Ямы возникают как промежутки между прямоугольниками пола.
Визуальное оформление краёв ям не входит в JSON и остаётся частью общего
каркаса арены.

У `solid_rect` есть необязательный флаг `one_way`:

```json
{
  "id": "bait_platform",
  "type": "solid_rect",
  "rect": [690, 416, 100, 20],
  "one_way": true
}
```

Пропущенный `one_way` канонически становится `false`. Обычный прямоугольник
блокирует тела со всех сторон, а односторонний позволяет запрыгнуть сквозь него
снизу и служит опорой сверху. В inspector это свойство выбирается через
`COLLISION → ONE WAY`, а preview выделяет такую платформу cyan-цветом. Для
линии огня оба варианта остаются твёрдым препятствием.

У каждого типа есть собственный небольшой набор свойств и допустимых диапазонов.
Например, `patrol_enemy` принимает скорость и начальное направление, но не путь
к скрипту. У толкача настраиваются позиция, начальное направление и закрытый
набор поведения:

```json
{
  "id": "shove_1",
  "type": "shove_enemy",
  "position": [800, 450],
  "direction": -1,
  "behavior_preset": "standard"
}
```

`behavior_preset` принимает только `standard` или `exam` и при пропуске
канонически становится `standard`. Вариант `exam` не открывает отдельные числа:
он выбирает зафиксированную связку из неподвижного толкача, зоны обнаружения
90 px и подготовки 1,4 секунды. Скорость рывка, его длительность и импульс
остаются общими. Пропущенный `direction` канонически становится `-1`.

Стрелок хранит позицию и тот же закрытый выбор поведения:

```json
{
  "id": "shooter_1",
  "type": "shooter_enemy",
  "position": [780, 450],
  "behavior_preset": "standard"
}
```

Дальность 900 px, тайминги прицеливания и перезарядки, геометрия дула,
скорость, радиус и импульс снаряда остаются внутри именованных presets.
`exam` даёт более длинную фиксацию и перезарядку из Arena 08, не меняя
геометрию или силу выстрела. На холсте выбранный стрелок поворачивается к точке
старта игрока и показывает линию огня. Линия обрезается первым `solid_rect`,
активной `toggle_platform` или настилом катапульты; неактивная платформа её не
блокирует.

Катапульта хранит позицию шарнира вращения и закрытый выбор импульса:

```json
{
  "id": "catapult_1",
  "type": "catapult_platform",
  "position": [180, 360],
  "behavior_preset": "standard"
}
```

В schema v1 катапульта всегда направлена вправо. В покое её настил размером
180×20 px лежит справа от указанной точки, а зона запуска занимает
180×52 px непосредственно над ним. Угол поворота −55° и тайминги едины;
`standard` использует импульс `(700, −280)`, а `exam` — слабый
`(180, −80)` для сброса цели в яму Arena 08. Произвольные компоненты импульса
в JSON по-прежнему запрещены. Validator проверяет настил и зону запуска;
поэтому допустимы позиции X от 32 до 748 и Y от 94 до 530.

У выбранной катапульты холст показывает зону запуска, крайнее положение
настила и первые 0,18 секунды траектории с фактическим knockback-drag цели.
Дуга помогает читать начальное направление и силу импульса, но не обещает точку
приземления: дальнейшее движение зависит от типа и текущей скорости тела,
окончания knockback-lock и столкновений. Это свободная направляющая центра
тела, она не обрезается потолком, полом или другими препятствиями. Placement,
drag, nudge и Duplicate удерживают pivot внутри допустимого диапазона.

Вертикальный лифт хранит только центр верхней остановки:

```json
{
  "id": "lift_1",
  "type": "vertical_platform",
  "position": [460, 330]
}
```

Корпус 80×20 px, нижняя остановка на 136 px ниже, старт сверху, предупреждение
0,25 секунды и движение за 1 секунду — закрытый игровой preset. Произвольные
дальность, направление, скорость и старт снизу в schema v1 не допускаются.
Центр верхней остановки ограничен X 72…888 и Y 82…394: верхняя граница
оставляет над настилом 40 px для пассажира, нижняя удерживает конечный корпус
внутри экрана.

Validator отдельно проверяет начальный настил, будущий sweep движущегося
корпуса и полный пассажирский коридор. Существо может стоять сверху, но не
стартовать под лифтом; неизменяемая геометрия и другие механизмы не могут
пересекать путь пассажира. При выделении холст показывает трек, обе остановки,
нижний ghost и кандидатов в пассажиры, которые окажутся на настиле после
оседания.

Включаемая платформа хранит прямоугольник и стартовое состояние:

```json
{
  "id": "bridge_1",
  "type": "toggle_platform",
  "rect": [400, 496, 160, 20],
  "starts_active": true
}
```

Шарнир ссылается на управляемый механизм только по стабильному ID:

```json
{
  "id": "hinge_1",
  "type": "hinge",
  "position": [300, 468],
  "target_id": "bridge_1"
}
```

Поле `starts_active` при чтении может отсутствовать и тогда канонически
становится `true`. Высота включаемой платформы в schema v1 равна 20 px,
ширина — не меньше 20 px. Тайминги переключения, `NodePath` и пути к сценам
остаются внутренними деталями игры и в JSON не допускаются.

Целью шарнира может быть `toggle_platform`, `catapult_platform` или
`vertical_platform`. Forward-ссылки разрешены, но отсутствующий ID, ссылка на
неподдерживаемый тип или на другой шарнир блокируют сохранение и тест.

Изменение смысла существующих полей требует новой `schema_version` и явной
миграции. Добавление новых типов в ту же версию допустимо только вместе с
обновлением validator и реестра типов.

Порядок уровней кампании не хранится внутри арены. Его задаёт отдельный
`campaign.json`, поэтому пользовательский уровень не может произвольно открыть
сцену через `next_arena_path`.

## Каталог кампании

Корневой `campaign.json` — единственный источник порядка и метаданных
встроенных уровней. Для каждой записи он хранит стабильный `level_id`, узкий
проектный путь `res://levels/*.json` и `catalog_title`:

```json
{
  "schema_version": 1,
  "campaign_id": "main",
  "advance_message": "АРЕНА ПРОЙДЕНА / ДАЛЬШЕ...",
  "final_behavior": "show_completion",
  "levels": [
    {
      "level_id": "arena_01_data",
      "path": "res://levels/arena_01.json",
      "catalog_title": "Arena 01 / Патруль"
    }
  ]
}
```

Положение записи в `levels` задаёт порядок прохождения. `CampaignStorage`
строго проверяет manifest, загружает и валидирует все перечисленные уровни до
старта и только затем отдаёт каталог `CampaignRunner` и редактору. ID и пути
не могут повторяться, путь ограничен каталогом `res://levels/`, а ID внутри
файла уровня обязан совпадать с записью manifest. Пользовательские уровни не
могут добавлять себя в эту встроенную кампанию.

Главная сцена проекта — `MainMenu`. Команда `НОВАЯ ИГРА` очищает запомненный
debug-выбор и открывает `CampaignRunner` с Arena 01. Во время заставки и игры
runner держит ровно один дочерний `LevelRuntimeArena`: победа переводит
Arena 01–07 вперёд по manifest, а `R` и падение пересоздают текущий runtime.
После Arena 08 `final_behavior: show_completion` удаляет runtime и показывает
отдельный экран завершения без автоматической загрузки уровня.

Первый уровень, обычный переход вперёд и прямой debug-выбор показывают короткую
заставку с `catalog_title`; restart по `R` и после падения её не повторяет.
Поверх runtime постоянно отображается прогресс `N / 8`. На финальном экране
`R` начинает кампанию с Arena 01, `Esc` возвращает в главное меню, а глобальное
меню `F1` остаётся доступным. Сохранения прогресса и команды `Продолжить` пока
нет.

## Безопасность данных

Файл уровня рассматривается как недоверенный ввод. Загрузчик:

- принимает только JSON-значения ожидаемых типов;
- не загружает указанные пользователем `res://` или `user://` пути;
- не создаёт произвольные классы, ресурсы, сигналы, методы или `NodePath`;
- разрешает только типы и свойства из внутреннего реестра;
- проверяет числовые значения на конечность и допустимый диапазон;
- ограничивает размер файла и количество элементов;
- принимает `level_id` только в формате `[a-z][a-z0-9_]*`, длиной до 64
  символов и без зарезервированных Windows-имён вроде `con` и `com1`;
- не записывает файлы за пределами каталога пользовательских уровней.

Конкретные начальные лимиты можно уточнить по профилированию, но validator
должен иметь явные верхние границы, например 256 KiB на файл и 512 объектов.
Это защищает и от случайно испорченных данных,
и от зависания Web-сборки.

## Хранение, импорт и экспорт

- встроенные примеры находятся в `res://levels/` и доступны только для чтения;
- созданные уровни сохраняются в `user://levels/`;
- изменяемый черновик и неизменяемая JSON-строка тестового снимка живут в
  памяти отдельно от опубликованных файлов;
- сохранение сначала записывает временный файл и заменяет целевой только после
  успешной сериализации и повторной валидации;
- прерванная запись восстанавливается при следующем открытии каталога:
  проверенный новый temp имеет приоритет над backup, а непонятный текущий файл
  сохраняется отдельно как quarantine-конфликт вместо удаления;
- успешное recovery показывает путь к сохранённому конфликту, а повреждённая
  запись остаётся видимой в списке как неактивная «требует внимания», не скрывая
  остальные уровни;
- замена файла, который не является текущим открытым пользовательским уровнем,
  требует отдельного подтверждения;
- встроенный уровень при редактировании сохраняется как пользовательская
  копия, а не перезаписывается;
- имя файла получается из проверенного `level_id`, но само поле остаётся
  источником идентичности уровня.

Системный диалог импорта и экспорта, а также удобный перенос файлов из
Web-сборки входят в более поздний этап. Базовый runtime должен одинаково уметь
читать встроенный и пользовательский JSON.

## Проверка уровня

### Ошибки, блокирующие сборку и тест

- корень JSON, обязательное поле или значение имеет неверный тип;
- версия схемы не поддерживается;
- ID пуст, небезопасен или повторяется;
- присутствует неизвестное поле, тип объекта или свойство;
- игрок отсутствует либо точек старта больше одной;
- противников нет;
- прямоугольник имеет нулевой или отрицательный размер;
- обязательный объект или его игровая область находится за экраном;
- стартовый коллайдер игрока или врага пересекает пол, внешнюю стену либо
  потолок;
- `target_id` отсутствует, указывает на самого себя либо ведёт к несовместимому
  типу;
- числовое свойство не входит в разрешённый диапазон;
- коридор движения платформы пересекает неизменяемую геометрию.

### Предупреждения

В schema v1 уже реализованы неблокирующие предупреждения:

- игрок или противник не имеет близкой твёрдой опоры под стартовой позицией;
- скорость патрульного равна нулю;
- у толкача меньше 48 px пола в начальном направлении патруля;
- включаемая платформа, катапульта или лифт не связаны ни с одним шарниром.

Активная включаемая платформа, настил катапульты и верхняя остановка лифта
считаются стартовой опорой и препятствием; неактивная платформа — нет. Более
сложные эвристики остаются следующими улучшениями:

- край патрульной поверхности находится слишком близко;
- шарнир, вероятно, нельзя достать игроком или разрешённой атакой;
- дуло стрелка сразу перекрыто;
- отключение платформы может оставить игрока без пути;
- механизм может выбросить участника за пределы ожидаемой ловушки;
- между стартом и противником не найден простой геометрический маршрут.

Validator не обязан доказывать решаемость action-puzzle. Сложные связи зависят
от времени, направления атак и навыка игрока, поэтому окончательная проверка —
короткий плейтест.

## Режим теста

В редакторе `F5` создаёт неизменяемый снимок текущего `LevelDraft`, проверяет
его и создаёт временный игровой runtime внутри живой сцены редактора:

- физика работает только в тестовой сцене, а не на preview-узлах редактора;
- `R` перезапускает тот же снимок, даже если файл ещё не сохранён;
- `Esc` возвращает в редактор с прежним черновиком, выделением и историей
  Undo/Redo;
- победа показывает результат, но не переводит в кампанию;
- debug-селектор арен отключён и во время редактирования, и в тесте;
- изменения состояния врагов и механизмов в тесте не попадают обратно в
  `LevelDraft`.

Кнопка `← Game` возвращает в источник перехода: редактор, открытый из главного
меню, возвращается в меню, а открытый через `F1` — на запомненную арену
кампании. В обычном режиме `Esc` последовательно сбрасывает активный инструмент,
снимает выделение и предлагает выход; изменённый черновик нельзя потерять без
подтверждения. Глобальный debug-селектор подавлен и в главном меню, и во всём
lifecycle редактора.

Один и тот же `LevelBuilder` используется тестом редактора, загрузкой
пользовательского файла и data-driven кампанией. Отдельная упрощённая
физическая модель для preview не создаётся.

## Этапы реализации

### 0. Data-driven фундамент

- добавить формат `schema_version: 1`, serializer, validator и реестр типов;
- выделить `LevelRuntimeArena` и `LevelBuilder`;
- воспроизвести Arena 01 из JSON без изменения её правил;
- проверить обычное отбрасывание, победу, падение и restart;
- оставить существующую цепочку из восьми `.tscn`-арен рабочей.

Этот этап реализован отдельной data-driven Arena 01. Интерфейс редактора
начинается на следующем этапе.

### 1. Минимальный редактор

- фиксированное поле 960×540 и видимая сетка с шагом 20 px;
- палитра из прямоугольного пола, точки старта и патрульного;
- выбор, размещение, перемещение, удаление и дублирование;
- панель разрешённых свойств выбранного объекта;
- Undo/Redo для всех изменений;
- создание, загрузка и безопасное сохранение уровня;
- список ошибок и предупреждений;
- запуск теста по `F5` и возврат по `Esc`.

Цель этого этапа — позволить самостоятельно собрать варианты Arena 01.

Этап реализован: вся арена видна на холсте в масштабе 0.6, доступны палитра,
drag-размещение, выбор и перемещение, inspector свойств, Undo/Redo,
неблокирующие предупреждения, безопасный каталог `user://levels/` и embedded
playtest без потери черновика, а также подтверждения выхода и перезаписи.

### 2. Связанные механизмы

- включаемая платформа;
- шарнир;
- режим связывания `hinge → target`;
- видимая линия связи и диагностика сломанных ссылок;
- предупреждения о недоступной опоре и возможном softlock.

После этого редактор должен собирать уровни масштаба Arena 02.

Этап реализован. Палитра создаёт включаемые платформы и шарниры; связь
назначается кликом по полю или через dropdown в inspector. Холст рисует линии
по ID, включая красный обрыв для удалённой цели. Builder разрешает
forward-ссылки отдельным проходом до добавления узлов в дерево, поэтому не
зависит от порядка объектов и не оставляет частично собранную арену. Реальный
smoke-плейтест ударом игрока отключает мост под патрульным и завершает уровень.
Геометрические эвристики достижимости шарнира и возможного softlock пока
остаются отдельным улучшением и не пытаются доказывать решаемость уровня.

Встроенный `arena_02_data` теперь повторяет исходные полы, яму, стартовые
позиции, скорость патрульного, мост 160×20 px и связь шарнира. Gameplay preset
и тайминги совпадают с ручной сценой. Общий runtime рисует прямой кабель вместо
ломаного декоративного, а встроенный playtest после победы перезапускает
snapshot. В основной кампании переходом к Arena 03 управляет `CampaignRunner`;
playtest редактора намеренно остаётся изолированным.

Встроенный `arena_06_data` повторяет пол, обе ямы, позиции игрока и стрелка,
узкую отключаемую опору и линию `shooter_hinge → shooter_platform`. Пассивная
приманка использует `solid_rect.one_way`, поэтому игрок может запрыгнуть на неё
снизу. После фиксации прицела нужно уйти влево: снаряд проходит через шарнир,
выключает опору стрелка и продолжает путь к прежней позиции игрока. В общем
runtime прямой cable заменяет ручную ломаную связь; декоративная направляющая,
отдельные подписи и переход к Arena 07 остаются за пределами JSON арены.

### 3. Полный набор прототипа

- толкач и стрелок;
- катапульта и вертикальный лифт;
- укрытия и остальные разрешённые параметры;
- специальные проверки линии огня, траектории запуска и коридора лифта.

Новые типы подключаются через реестр и типизированные descriptors, а не через
условия, размазанные по интерфейсу.

Первый вертикальный срез этапа реализован для `shove_enemy`. Validator учитывает
его как полноценного врага и проверяет коллайдер 32×38; builder создаёт
закрытый именованный preset независимо от порядка объектов в JSON. Холст
показывает отдельный красный силуэт, направление патруля и у выбранного объекта
фактическую симметричную зону обнаружения текущего preset. Прокручиваемые секции
палитры оставляют место следующим типам. Встроенный `arena_03_data` проверяет
подготовку, рывок, отбрасывание игрока и победу ответным ударом в центральную
яму.

Второй вертикальный срез реализован для `shooter_enemy`. Его закрытый контракт
содержит позицию и именованный preset, а validator проверяет коллайдер 34×38.
Инструмент `7 СТРЕЛОК`, hit-test, drag, nudge, Duplicate и inspector работают
с тем же Undo/Redo-потоком. Preview использует реальные смещение шарнира оружия,
длину дула, радиус снаряда и дальность, показывает игрока вне дальности
пунктиром и обрезает линию ближайшим твёрдым препятствием. Встроенный
`arena_05_data` проверяет укрытие, настоящий выстрел и победу столкновением
стрелка в яму. Снаряды принадлежат временной арене, поэтому не переживают
остановку или restart playtest.

Третий вертикальный срез реализован для `catapult_platform`. Формат хранит
позицию шарнира и именованный preset, а направление, размер, угол, тайминги и
два разрешённых импульса остаются закрытыми. Общий механизм связей принимает и
включаемую платформу, и катапульту. Инструмент `8 КАТАПУЛЬТА`, hit-test, drag,
nudge, Duplicate и inspector используют общий Undo/Redo-поток; preview
показывает фактическую зону запуска, крайнее положение настила и стартовую
дугу. Встроенный `arena_04_data` проверяет настоящий импульс, запуск
патрульного в центральную яму, возврат платформы и безопасную остановку
активной анимации вместе с embedded playtest.

Четвёртый вертикальный срез реализован для `vertical_platform`. Закрытый
контракт содержит только центр верхней остановки; корпус 80×20 px, ход вниз
136 px, стартовое состояние и тайминги остаются единым preset. Validator
различает начальную опору, sweep корпуса и пассажирский clearance, запрещая
старт существ под лифтом и пересечение пути с геометрией. Инструмент `9 ЛИФТ`
показывает обе остановки, коридор и нижний ghost; inspector оставляет
редактируемыми только X и Y. Встроенный `arena_07_data` проверяет перевозку
стрелка, смену блокировки линии огня укрытием и победу столкновением в шахту.

Встроенный `arena_08_data` объединяет все три типа врагов и все три механизма.
Закрытый `exam`-preset точно сохраняет длинную провокацию толкача, слабый
импульс катапульты и более медленный прицел стрелка из ручной сцены. Решение
остаётся последовательным: рывок выключает мост, катапульта сбрасывает
патрульного, лифт опускает стрелка за укрытие, после чего его можно выбить в
правую шахту.

### 4. Миграция кампании

Этап реализован:

- порядок, ID, пути и названия вынесены в единый `campaign.json`;
- `CampaignStorage` атомарно проверяет manifest и все восемь JSON-уровней;
- `MainMenu` стал главной сценой, а `CampaignRunner` управляет игровыми
  переходами и restart;
- campaign UI показывает заставку при входе в новую арену, прогресс `N / 8`
  и отдельный экран завершения после Arena 08;
- debug-селектор переключает уровни внутри runner по данным manifest;
- campaign smoke фиксирует порядок Arena 01–08, обычный переход, `R`, падение,
  прямой debug-переход, гонку restart с задержкой после победы и завершение
  кампании с новым стартом на Arena 01;
- main-menu smoke фиксирует маршрут `меню → Arena 01 → меню → редактор → меню`,
  очистку debug-выбора и изоляцию глобального селектора;
- ручные `.tscn` исключены из основного запуска и сохранены только как
  reference/regression-эталоны.

## Что не входит в ближайший объём

- редактирование и сохранение `.tscn`;
- произвольные GDScript, сцены, ресурсы и пользовательские ассеты;
- изменение поведения существ или создание новых механик внутри редактора;
- доказательство решаемости уровня;
- процедурная генерация;
- совместное сетевое редактирование, облачная публикация и каталог уровней;
- скриптовые события, кат-сцены, диалоги и ветвление кампании;
- финальная графика, анимация таймлайна и универсальный tilemap-редактор;
- удаление исходных `.tscn`: пока они нужны как regression/reference после
  миграции.

## Критерии готовности фундамента

Этап 0 считается завершённым, когда:

- Arena 01 описана версионированным JSON без путей к сценам или скриптам;
- validator принимает корректный файл и выдаёт стабильные понятные ошибки на
  некорректных fixtures;
- `LevelBuilder` собирает левый и правый пол, игрока и патрульного в общем
  `LevelRuntimeArena`;
- стартовые положения, размеры пола и параметры патруля совпадают с исходной
  Arena 01;
- игровыми действиями проверены устранение противника, победа, падение игрока и
  `R`-restart;
- неизвестные типы, свойства, повторяющиеся ID и неверные связи не приводят к
  частичной загрузке или выполнению кода;
- JSON загружается в headless-режиме без ошибок парсинга и Godot;
- встроенные восемь JSON-арен проходят через `CampaignRunner`, а ручные сцены
  остаются отдельно запускаемыми regression-эталонами;
- формат и ограничения описаны в этом документе.

Редактор проходит этот критерий: автор может собрать, сохранить, повторно
открыть и пройти data-driven варианты всех Arena 01–08, включая экзамен с тремя
последовательными связками, не редактируя сцены Godot. Кампания использует тот
же runtime-builder, но embedded playtest по-прежнему перезапускает только
неизменяемый снимок редактируемого уровня.
